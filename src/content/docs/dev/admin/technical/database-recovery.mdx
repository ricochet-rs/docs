Recover a server that will not start because an upgrade hit a foreign key error.

```text
Error: while executing migration <timestamp>: error returned from database: (code: 787) FOREIGN KEY constraint failed
```

The timestamp changes between releases.
What stays constant is the code `787` and the phrase `FOREIGN KEY constraint failed`.

The database holds tables that the installed release does not know about, left behind by a pre-release build that ran against the same file.
An upgrade that rebuilds a table checks every foreign key in the database when it finishes, and those extra tables fail the check.
Dropping them clears the error.

<Aside type="caution">
  Back up `ricochet.sqlite3` before you start.
  Dropping a table deletes the rows in it, and only pre-release builds ever wrote to these tables.
</Aside>

## Find the tables to drop

Ask a server that still answers:

```sh
ricochet db doctor -S https://your-ricochet-server
```

The command needs the [ricochet CLI](/dev/user/quickstart/) and an admin API key, which `ricochet login` configures.
A healthy database reports:

```text
✓ Database schema matches the expected schema for this server build.
```

Otherwise the report names the tables to drop:

```text
✗ Database schema drift detected.

Phantom tables (in database, not in expected schema)
┌─────────────────────┐
│ Name                │
╞═════════════════════╡
│ deployment_runtimes │
├─────────────────────┤
│ exec_env_checks     │
└─────────────────────┘

Summary: 2 phantom table(s), 0 missing table(s), 0 table(s) with shape drift
```

Add `--format json` to pipe the report into other tooling.
The same report is served at `GET /api/admin/db/doctor`, and the server writes it to the log at startup whenever the database and the build disagree.

When nothing is running, read the file directly.
The error message names the table the upgrade was rebuilding, `deployments` in this example:

```sh
sqlite3 /data/ricochet.sqlite3 "
SELECT m.name FROM sqlite_master m, pragma_foreign_key_list(m.name) p
WHERE m.type = 'table' AND p.\"table\" = 'deployments';"
```

The result lists every table pointing at it.
Any name the release itself does not use is a leftover to drop.

## Recover

The steps below use Kubernetes.
On a host install, stop the service, run the same `sqlite3` commands, then start it again.

<Steps>

1. **Stop the server so the database file is not held open.**

    ```sh
    kubectl -n ricochet scale deploy ricochet --replicas=0
    kubectl -n ricochet rollout status deploy/ricochet --timeout=60s
    ```

2. **Start a pod that sleeps instead of running the upgrade.**

    ```sh
    kubectl -n ricochet patch deploy ricochet --type=json -p='[
      {"op":"replace","path":"/spec/template/spec/containers/0/command","value":["sleep","infinity"]},
      {"op":"replace","path":"/spec/template/spec/containers/0/args","value":[]}
    ]'
    kubectl -n ricochet scale deploy ricochet --replicas=1
    kubectl -n ricochet rollout status deploy/ricochet --timeout=120s
    ```

3. **Open a shell in the pod and confirm you own the database file.**

    ```sh
    POD=$(kubectl -n ricochet get pod -l app.kubernetes.io/name=ricochet -o jsonpath='{.items[0].metadata.name}')
    kubectl -n ricochet exec -it "$POD" -c ricochet-helm -- sh
    id
    ls -ln /data/ricochet.sqlite3
    ```

    The `uid` from `id` must match the file owner, commonly `1000`.
    A mismatch opens the database read-only and the next step fails with `attempt to write a readonly database`.

4. **Back up the file, then drop the tables from the report.**

    ```sh
    sqlite3 /data/ricochet.sqlite3 \
      ".backup '/data/ricochet.pre-cleanup-$(date -u +%Y%m%dT%H%M%SZ).sqlite3'"

    sqlite3 /data/ricochet.sqlite3 <<'SQL'
    PRAGMA foreign_keys = ON;
    DROP TABLE IF EXISTS deployment_runtimes;
    DROP TABLE IF EXISTS exec_env_checks;
    PRAGMA foreign_key_check;
    SQL
    ```

    `foreign_key_check` must return nothing.
    If it returns rows, restore the backup and stop here.

5. **Restore the original command and let the upgrade finish.**

    ```sh
    kubectl -n ricochet patch deploy ricochet --type=json -p='[
      {"op":"remove","path":"/spec/template/spec/containers/0/command"},
      {"op":"remove","path":"/spec/template/spec/containers/0/args"}
    ]'
    kubectl -n ricochet rollout status deploy/ricochet --timeout=180s
    kubectl -n ricochet logs -f deploy/ricochet -c ricochet-helm
    ```

    The server reaches its normal startup line and the `787` error is gone.
    If it is not, restore the backup from step 4 before doing anything else.

</Steps>

## Prevention

Upgrade between release tags only.
A pre-release build can add tables that never ship, and they stay behind when you move to a release.
Test a pre-release build against a copy of the database, not the production file.
