ricochet uses OpenID Connect (OIDC) for authentication, allowing you to integrate with any OIDC-compliant identity provider.

## Requirements

The OIDC provider must support:

- **Claims**: `email` and `profile`
- **Grant Type**: Authorization Code Flow
- **PKCE**: code challenge with the `S256` method

ricochet uses the subject identifier (`sub`) as the unique user ID.
The `email` claim is collected for future SMTP integrations.

Every sign-in sends a PKCE challenge and the matching verifier on the token exchange, so the client registration must permit PKCE.
If your provider exposes a PKCE setting, set it to `S256`.
PKCE cannot be turned off.

Because PKCE protects the flow, `client_secret` is optional and ricochet can run as a public client.
Microsoft Entra group and avatar sync is the exception, it needs the secret to call Microsoft Graph.

## Configuration

Add the following to your `ricochet-config.toml`:

```toml
[auth.oidc]
issuer_url = "https://auth.example.com/"
client_id = "your_client_id"
client_secret = "your_client_secret"
redirect_url = "https://your-ricochet-domain.com/oauth/callback"
display_name_claim = "preferred_username"  # Optional, defaults to "preferred_username"
groups_claim = "groups"  # Optional, defaults to "groups"
```

<Aside type="caution">
  The redirect URL **must** use the `/oauth/callback` path for compatibility with the ricochet cli.
</Aside>

#### Configuration Fields

| Field                | Required | Description                                                                                                    |
| -------------------- | -------- | -------------------------------------------------------------------------------------------------------------- |
| `issuer_url`         | Yes      | Your OIDC provider's issuer URL. Must start with `https://`                                                    |
| `client_id`          | Yes      | OAuth client ID from your OIDC provider                                                                        |
| `client_secret`      | No       | OAuth client secret from your OIDC provider. Omit it to register ricochet as a public client. Microsoft Entra group and avatar sync requires it. |
| `redirect_url`       | Yes      | Callback URL where users are redirected after authentication. **Must be** `https://your-domain/oauth/callback` |
| `display_name_claim` | No       | OIDC claim to use for display name. Defaults to `preferred_username`                                           |
| `groups_claim`       | No       | Name of the OIDC claim that carries the user's group memberships. The claim value may be an array of strings, a single string, or a comma-delimited string. Omit to disable group sync at login. |
| `provider`           | No       | Identity provider variant. Set to `"entra"` for Microsoft Entra ID; omit or set to `"oidc"` for all other providers. When `"entra"`, `groups_claim` defaults to `"groups"` and background directory sync is enabled. |
| `sync_interval`      | No       | How often (in minutes) to run background group sync from the IdP directory. Only supported when `provider = "entra"`. Omit to sync group memberships at login only. |

## SSO Groups

When `groups_claim` is set (defaulted to `"groups"`), ricochet reads the user's group memberships from the configured claim of every ID token at login and mirrors them into the local `user_groups` table.
You can then grant a role on a content item to a group name via the collaborators dialog, and any user whose ID token carried that group at their last login inherits the role.

A few practical points:

- **Group memberships refresh on every login.** A user who was added to a group in your IdP after their last ricochet login will not pick up the role until they sign in again.
- **Names are byte-equal and case-sensitive.** The group name typed in the collaborators dialog must match the string in the ID token exactly.

## Microsoft Entra ID (Azure AD)

### Issuer URL

When using Microsoft Entra ID, you must use the v2.0 issuer URL.
The v1 issuer (`https://sts.windows.net/{tenant-id}/`) returns a non-standard discovery document that is incompatible with ricochet's OIDC client.

```toml
[auth.oidc]
provider = "entra"
issuer_url = "https://login.microsoftonline.com/{tenant-id}/v2.0"
client_id = "your_client_id"
client_secret = "your_client_secret"
redirect_url = "https://your-ricochet-domain.com/oauth/callback"
```

Replace `{tenant-id}` with your Azure tenant ID.

### Groups claim

Entra does not emit a `groups` claim by default — enable it explicitly on the app registration under *Token configuration → Add groups claim*.
Pick *Group ID* (the default) or *sAMAccountName* depending on what your tenant supports.

<Aside type="caution">
  Entra emits **group object IDs (GUIDs)** for cloud-only groups, even when `sAMAccountName` format is selected — `sAMAccountName` is only populated for groups synchronized from on-premises Active Directory via Entra Connect.
  If your groups were created directly in Entra, the value in the `groups` claim will be a GUID like `a3f2c1e8-...`.
  ricochet resolves these GUIDs to display names via Microsoft Graph when `provider = "entra"` is set.
</Aside>

<Aside type="note">
  Background directory sync requires the app registration to have the **`Group.Read.All`** Microsoft Graph application permission granted by an administrator.
  Without it, ricochet can still sync group memberships at login from the ID token but cannot pull display names from the Graph API.
</Aside>

### User avatars

Standard OIDC providers populate user avatars from the `picture` claim, but Entra omits that claim and serves photos only from Microsoft Graph.
When `provider = "entra"` is set, ricochet fetches each user's photo at login from `GET /users/{id}/photo/$value`, resizes it to a 128×128 PNG, and stores it without overwriting a user-uploaded avatar.

<Aside type="note">
  Fetching avatars requires the app registration to have the **`User.Read.All`** Microsoft Graph application permission granted by an administrator (admin consent).
  The group permissions above do not cover `/users/{id}/photo`.
  Avatar fetching is best-effort — a missing permission, missing photo, or missing `oid` claim never blocks login.
</Aside>

<Aside type="note">
  Entra applies a "group overage" limit at roughly 200 group memberships per user.
  Beyond that point Entra stops embedding the groups array in the token and references it via Microsoft Graph instead, which ricochet does not currently follow.
  Users with very large group memberships will appear to have no groups until this is implemented.
</Aside>

## Auth0

In Auth0, create a **Regular Web Application** and add `https://your-ricochet-domain.com/oauth/callback` to its **Allowed Callback URLs**.
Copy the **Domain**, **Client ID**, and **Client Secret** from the application's **Settings** tab.

```toml
[auth.oidc]
issuer_url = "https://{tenant}.auth0.com/"
client_id = "your_client_id"
client_secret = "your_client_secret"
redirect_url = "https://your-ricochet-domain.com/oauth/callback"
display_name_claim = "name"
groups_claim = "https://ricochet.example.com/groups"
```

Replace `https://{tenant}.auth0.com/` with the **Domain** of your application, or with your Auth0 custom domain if users sign in through one.

### Display name

Auth0 does not send `preferred_username` for most connections, so set `display_name_claim` to `name` or `email`.

### Groups claim

Auth0 puts no groups in the ID token.
To share content with groups, add a post-login Action under **Actions → Triggers → post-login** that copies the user's Auth0 roles into a namespaced claim:

```js
exports.onExecutePostLogin = async (event, api) => {
  api.idToken.setCustomClaim(
    "https://ricochet.example.com/groups",
    event.authorization?.roles ?? [],
  );
};
```

Set `groups_claim` to the full claim name, including the `https://` namespace.
Grant a role on content to an Auth0 role name in the collaborators dialog, exactly as it appears in Auth0.

## Keycloak

In your realm, create an **OpenID Connect** client with **Client authentication** and **Standard flow** turned on.
Add `https://your-ricochet-domain.com/oauth/callback` to **Valid redirect URIs**, then copy the secret from the **Credentials** tab.

```toml
[auth.oidc]
issuer_url = "https://keycloak.example.com/realms/{realm}"
client_id = "your_client_id"
client_secret = "your_client_secret"
redirect_url = "https://your-ricochet-domain.com/oauth/callback"
groups_claim = "groups"
```

Replace `{realm}` with your realm name.

### Groups claim

Keycloak puts no groups in the ID token by default.
Open the client's **Client scopes** tab, select the `-dedicated` scope, and add a **Group Membership** mapper with **Token Claim Name** set to `groups`.
Turn off **Full group path** so the claim carries `analysts` rather than `/analysts`.

## ZITADEL

In a ZITADEL project, create a **Web** application with the **Code** authentication method.
Add `https://your-ricochet-domain.com/oauth/callback` to its **Redirect URIs**, then copy the client ID and secret.

```toml
[auth.oidc]
issuer_url = "https://your-instance.zitadel.cloud"
client_id = "your_client_id"
client_secret = "your_client_secret"
redirect_url = "https://your-ricochet-domain.com/oauth/callback"
groups_claim = "groups"
```

Use the instance domain shown in the ZITADEL console as the issuer URL.

### Groups claim

ZITADEL sends project roles as an object, which ricochet cannot read as groups.
Add an Action that writes the user's roles into a flat `groups` claim:

```js
function groups(ctx, api) {
  if (ctx.v1.user.grants == undefined) {
    return;
  }
  let roles = [];
  ctx.v1.user.grants.grants.forEach((grant) => {
    grant.roles.forEach((role) => roles.push(role));
  });
  api.v1.claims.setClaim("groups", roles);
}
```

Attach the Action to the **Complement Token** flow on the **Pre Userinfo creation** trigger.
In the application's **Token Settings**, turn on **User Info inside ID Token** so the claim reaches ricochet.

## authentik

Create an application with an **OAuth2/OpenID Provider** whose **Client type** is **Confidential**.
Add `https://your-ricochet-domain.com/oauth/callback` as a strict **Redirect URI**, then copy the client ID and secret from the provider.

```toml
[auth.oidc]
issuer_url = "https://authentik.example.com/application/o/{application-slug}/"
client_id = "your_client_id"
client_secret = "your_client_secret"
redirect_url = "https://your-ricochet-domain.com/oauth/callback"
groups_claim = "groups"
```

Replace `{application-slug}` with the slug of the authentik application.
authentik's default `profile` scope already sends the user's group names in the `groups` claim.

## Requiring Authentication

By default, unauthenticated users can browse the "Explore" page and view public content.
To require authentication for all access, enable the `require_authentication` option:

```toml
[auth]
require_authentication = true
```

Or via environment variable:

```bash
RICOCHET_AUTH__REQUIRE_AUTHENTICATION=true
```

### Behavior

| Setting                        | Unauthenticated User Access                          |
| ------------------------------ | ---------------------------------------------------- |
| `require_authentication=false` | Can view Explore page and public content only        |
| `require_authentication=true`  | Redirected to sign-in page on all routes             |

When `require_authentication` is enabled, users see a full-screen login page with SSO sign-in.
When disabled (the default), unauthenticated users can browse public content but see a sign-in prompt in the sidebar to access protected features like deployment, API keys, and settings.
